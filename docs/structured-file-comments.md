# 構造化ファイルコメント

## 目的

Feature Context Builderは、ファイル名だけでなく「どの機能に属し、何を担い、どこから呼ばれるか」をローカルで検索できるようにします。そのため、重要なソースファイルの先頭へ、人と機械の両方が読める短い構造化コメントを置きます。

コメントはコードを置き換える仕様書ではありません。検索の入口と、変更時の注意を共有するための索引です。

## 基本形式

```ts
/**
 * @feature-context
 * @feature 認証, ログイン, login, auth
 * @role ログイン画面から認証処理を開始する
 * @entry LoginPage
 * @flow LoginPage -> AuthService.login -> POST /api/login
 * @related AuthService, TokenStore
 * @caution 認証成功後にだけTokenStoreへ保存する
 */
```

`@feature-context`、`@feature`、`@role`が基本です。残りは該当する情報がある場合に使います。

| タグ | 必須 | 意味 |
|---|---|---|
| `@feature-context` | はい | 構造化コメントであることを示すmarker |
| `@feature` | はい | 日本語・英語の機能名、同義語、関連語 |
| `@role` | はい | ファイルの責務 |
| `@entry` | 任意 | 外部から呼ばれる主な入口 |
| `@flow` | 任意 | 入口から出口までの短い流れ |
| `@related` | 任意 | 密接に関連するシンボルまたはファイル |
| `@caution` | 任意 | 変更時に守る契約や注意点 |

複数値はカンマ、読点、`|`で区切れます。同じタグを複数行書くこともできます。

## 何を、どの粒度で書くか

コメントはファイルの全処理を説明する場所ではありません。ファイルをまだ開いていない人や探索処理が、次を判断できる最小限の情報を残します。

1. 調べたい機能に関係するか
2. そのファイルが何を決めるか
3. どこから処理が入り、どこへ出るか
4. 一緒に確認すべきfileやsymbolは何か
5. 変更時に壊しやすい契約は何か

### タグごとの判断基準

| タグ | 書く内容 | 避ける内容 |
|---|---|---|
| `@feature` | 利用者が検索しそうな機能名、ドメイン語、英日同義語 | module名や一般語の無差別な列挙 |
| `@role` | 「何を知り、何を決めるファイルか」を1文で表した責務 | private関数を順番に説明する実況 |
| `@entry` | 外部から呼ばれる主なfunction、class、command、route、component | file内の全symbol |
| `@flow` | 入口、主要処理、出口を短くつないだ流れ | 全分岐、例外処理、細かな内部手順 |
| `@related` | 一緒に変更判断が必要な密接なsymbol・file | import一覧の複製 |
| `@caution` | 互換性、安全性、順序、再試行、永続化などの壊しやすい契約 | 担当者、日付、一時的なTODO、変更履歴 |

`@role`は「各種処理を行う」「共通機能を提供する」のような曖昧な表現を避けます。`@caution`には理想や未確定仕様ではなく、現在の実装が実際に守っている契約を書きます。

## 付ける対象と例外

次のfileには追加します。

- 新しく作る、プロジェクト所有の実装file
- 責務、主要flow、外部との境界を変更したfile
- 名前だけでは所属機能を判断しにくい設定、adapter、共通処理
- `src/discovery`配下の実装file

次は原則として対象外です。

- 生成コード、vendor、外部から取り込んだコード
- 型宣言だけのfile
- 単純な再exportだけのfile
- 独立した責務を持たず、内容が自明な小さなfile

過去の変更内容はGit、未完了作業はissueやTODOへ残します。構造化コメントを変更履歴の保管場所にはしません。

## 対応するコメント形式

- JavaScript、TypeScript、Java、C#などの`/* ... */`
- Pythonなどの`# ...`
- JavaScriptなどの連続した`// ...`
- SQL、Luaなどの連続した`-- ...`
- Pythonの先頭docstring
- HTML、Vueなどの`<!-- ... -->`

ファイル先頭16,384文字以内に置いてください。

## 運用

1. 新しい重要ファイルを作るときにコメントを追加する
2. 責務、入口、主要依存を変更したときにコメントも更新する
3. 生成コード、vendor、単純な型・再exportには追加しない
4. コメントと実装が食い違う場合は実装を正とし、コメントを修正する
5. AIが書いたコメントもレビュー対象にする

変更時には、`@feature`の検索語、`@role`の責務、`@entry`の公開入口、`@flow`の主要経路、`@related`の密接な関係、`@caution`の契約が現在の実装と一致するかを確認します。内部実装だけを変更し、これらが変わらない場合は、コメントを無理に書き換える必要はありません。

コメント本文は信頼できない入力として扱われます。パス検証、秘密情報検査、実コード確認を迂回する権限は持ちません。
